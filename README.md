# DevSecOps IaC Security Pipeline

A security gate for Terraform. It scans infrastructure code for dangerous
misconfigurations, blocks a pull request that introduces them, publishes
findings to GitHub's Security tab, and refuses to let credentials be
committed. It also tests *itself*, so you can trust that the gate would
actually fire.

## Why this exists

Most cloud security incidents come from ordinary misconfigurations: a public
bucket, SSH open to the internet, an admin policy with `*` on everything.
These are cheap to catch in code review and expensive to catch in
production. This project catches them automatically, before merge.

so numbers will shift.

## How it works

```
developer commits
   |-- pre-commit: Checkov gate + detect-secrets   (local, before the commit exists)
   v
pull request
   |-- GitHub Actions: iac-gate
   |      checkov on terraform/hardened  -> any finding fails the check
   |      pytest (8 tests)               -> proves the gate itself works
   v
push to main
   |-- GitHub Actions: findings-report
          checkov on terraform/insecure -> SARIF -> GitHub Security tab
```

## What is in the repo

| Path | Purpose |
|---|---|
| `terraform/insecure/` | Deliberately vulnerable AWS stack (public bucket, open SSH, wildcard IAM, no key rotation). **Never apply it.** |
| `terraform/hardened/` | The same building blocks, fixed. Skips carry written reasons. |
| `custom_policies/s3_owner_tag.yaml` | A custom organisation rule: every S3 bucket needs an `Owner` tag. |
| `tests/test_security_gate.py` | 8 policy-as-code tests (see below). |
| `scripts/scan_report.py` | Runs both scans and writes `REPORT.md`. |
| `.github/workflows/security-pipeline.yml` | The CI pipeline. |
| `.pre-commit-config.yaml` | Local hooks running the same checks. |

## How to test it

**Prerequisite:** Python 3.11 or 3.12 (verified on 3.12). Checkov does not
always support the newest Python release, so avoid brand-new versions.

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate      Mac/Linux: source .venv/bin/activate
pip install -r requirements-dev.txt
```

**1. Run the test suite**
```bash
python -m pytest -v
```
Expected: `8 passed`. The tests check that:
- the hardened stack has zero failed checks
- the insecure stack is caught (24 failures, including the five critical controls: public ACL, open SSH, wildcard IAM, KMS rotation, S3 encryption)
- the custom Owner-tag policy runs on both stacks
- every skipped check has a real written justification
- a simulated bad pull request (SSH opened to `0.0.0.0/0`) is blocked
- the repository contains no secrets
- the secret scanner really detects a planted key (a positive control)

**2. Regenerate the before/after report**
```bash
python scripts/scan_report.py
```

**3. Try the local hooks**
```bash
git init && git add -A
pre-commit install
pre-commit run --all-files          # both hooks pass
```
Then change `admin_cidr` in `terraform/hardened/main.tf` to `"0.0.0.0/0"`,
stage it, and run `pre-commit run --all-files`. The Checkov hook fails.
Revert the change afterwards.

**4. See it block a real pull request (the best screenshot)**
1. Push the repo to GitHub and let the workflow run once on `main` (green).
2. Create a branch, change `admin_cidr` to `"0.0.0.0/0"`, open a pull request.
3. The **IaC security gate (blocking)** check fails with a red X.
4. To make that check actually *prevent merging*: Settings > Branches > add a
   protection rule for `main` and require the status check
   `IaC security gate (blocking)`.

**5. See findings in the Security tab**
After a push to `main`, open Security > Code scanning. This needs a public
repository (or GitHub Advanced Security on a private one).

## What has and has not been verified

Verified by running it: both scans and their numbers, all 8 tests (from a
fresh install of `requirements-dev.txt`), the report script, the pre-commit
hooks (clean repo passes; a planted credential is blocked; an
SSH-to-the-world change is blocked), that the SARIF file is produced at the
exact path the workflow uploads from, and that every YAML file parses.

Not verified: the GitHub Actions workflow itself has not been executed, and
the Security-tab upload and branch protection need a real repository. The
first push is the real test. If a step fails, the log will say which one.

## Honest limitations

- Static scanning finds configuration mistakes, not runtime attacks or logic
  flaws. It complements, and does not replace, review and monitoring.
- Checkov flags best-practice gaps as well as real vulnerabilities (for
  example cross-region replication). The hardened stack skips five of these
  with written reasons; a skip without a reason fails the test suite.
- Lesson from building it: `detect-secrets` silently returns zero findings if
  you point it at an absolute path outside the current directory. The tests
  run it from inside the target folder and include a positive control, so a
  broken scanner cannot make the secrets test pass by accident.
